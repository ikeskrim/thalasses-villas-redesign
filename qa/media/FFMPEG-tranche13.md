# The owner-video path with a real ffmpeg (tranche thirteen)

DECISIONS.md D-021: install ffmpeg and verify the video path on a dummy clip. Everything below was run on 2026-09-14, and every clip was generated by ffmpeg's own test sources: nothing here is property imagery.

## The install

- **Package:** `winget install --id Gyan.FFmpeg --exact --source winget --scope user`. The gyan.dev full build is the Windows build ffmpeg.org links to.
- **Version:** 9.0.1 (`ffmpeg version 9.0.1-full_build-www.gyan.dev`), installed per user under `%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg_…\ffmpeg-9.0.1-full_build\bin\`, where `ffprobe.exe` sits beside `ffmpeg.exe`.
- **Encoders:** libx264 present, libvpx-vp9 present.
- **Finding it:**
  - winget reported "command line alias added" and changed the user PATH.
  - No alias shim was found under `%LOCALAPPDATA%\Microsoft\WinGet\Links`, and a shell started before the install does not see the new PATH.
  - So the pipeline was pointed at the binary through `FFMPEG_PATH`, as an absolute path. That is the dependable form on this machine, and the one servers launched through WMI can see.

## The check

`ffmpeg-verify.mjs`, from the session scratch, drives the real command from the repository root. For each case it hand-writes a manifest in the exact shape the ingest writes (a `needs-transcode` entry with its recorded commands), in an output root outside the repository:

```bash
INGEST_OUT_ROOT=<work>/<case> FFMPEG_PATH=<ffmpeg.exe> node scripts/ingest-drive.mjs --transcode-pending
```

It then inspects the outputs with ffprobe, because the pipeline itself checks only the exit status, that the file exists, and the byte budget.

## Found: VP9 cannot hold the budget on pathological input

The same 8-second, 1920-wide, silent VP9 cut (`-row-mt 1 -deadline good`) was re-run with four rate-control settings:

| input | setting | bytes | within 2,621,440 | seconds |
|---|---|---|---|---|
| testsrc2 | current: `-b:v 2411k -maxrate 2411k -bufsize 4822k` | 2,044,050 | yes | 10.1 |
| testsrc2 | CBR: add `-minrate 2411k` | 2,382,831 | yes | 10.8 |
| testsrc2 | constrained quality: `-crf 36 -b:v 2411k` | 1,592,643 | yes | 9.2 |
| testsrc2 | constrained quality plus `-maxrate 2411k -bufsize 4822k` | 1,592,643 | yes | 9.6 |
| noise | current | 17,225,636 | no | 58.0 |
| noise | CBR | 11,985,922 | no | 58.5 |
| noise | constrained quality | 17,225,636 | no | 62.5 |
| noise | constrained quality plus maxrate | 17,225,636 | no | 66.3 |

What that means:

- **No single-pass VP9 setting holds full-strength noise at 1080p within the budget.** H.264 at the same target did.
- **The pipeline fails loudly, as designed.** Nothing over budget is ever marked ready.
- **Real footage is not synthetic noise.** Whether the owner's MP4 or phone video comes near this is not established until those clips arrive.
- **The encoder settings were not changed.** The fallback is an editorial and design call, not an encoder flag: a lower-resolution WebM, or MP4 alone, when the WebM is over budget.
